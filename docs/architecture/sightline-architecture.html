Architecture · Sightline

From drone photos to where to search next

A detector reads every drone photo and ranks them for a human searcher; each confirmed person becomes a pin on the map, and a Bayesian probability map shows where the person could still be. Four lanes, one contract between them.

The system

Lane D's pipeline calls the other three lanes, writes one validated cache, and the website only ever reads it.

The ML pipeline

Trained and tested once on HERIDAL, then the same weights and the same 0.29 threshold score every survey.

A live mission

Sprint 2: the same detector and map per photo, while the search happens. On AWS (deploy/aws/) the API and the worker are containers on one EC2 instance; locally the queue is a thread.

The agent

Perception, decision, action, approval, effect. OpenCV 5 re-looks at what the detector wasn't sure of; Nemotron VL and the planner turn it into proposals; nothing happens until a person approves, and every step is in the trace.

Why tiles

A person is about 70 px wide in a 4000×3000 photo. Shrinking the photo to the model's input loses them, so the detector trains and runs on overlapping 1024 px tiles at full resolution. Tiling takes fine-tuned recall from 0.234 to 0.864 on the test set.

Honest by construction

  • The threshold is chosen on validation, never on test
  • Ground truth never enters the cache
  • Every cache file is checked against contract 1.1
  • Simulated parts are labelled on screen

Where the numbers come from

metrics.json (HERIDAL test set, 101 photos, 337 people; demo ranking), the weights-v2 release, and scripts/README.md. Limits and failure cases: docs/DETECTOR_LIMITS.md.
